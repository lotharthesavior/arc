Arc developer experience proposal

Fresh app.
Zero cloning.

Design the missing product surface: a published arc-web-cli package that installs the arc command and creates a self-contained, runnable Arc application.

cargo install arc-web-cli arc new my-app cd my-app make setup make dev

Target promise: those five commands take a developer from an empty directory to a visible server—or a precise, actionable error.

Outcome

The contract we are designing

Self-contained

No Arc checkout

The generated app depends on published crates and owns its migrations, environment, and project files.

Observable

No silent exits

Logging initializes first. Database, bind, and configuration failures print a direct explanation and next action.

Repeatable

Tested externally

Release verification scaffolds into a clean temporary directory, builds, migrates, starts, and probes health.

Primary decision

How should the starter ship?

Recommended

Published arc-web-cli

Install once with Cargo. The binary embeds a template matching its release.

  • Exact five-command experience
  • Works offline after installation
  • Arc-specific validation and upgrades later
  • New crate and release responsibility
Alternative

cargo-generate

Use a generic generator and a remote template repository.

  • Less CLI code
  • Extra tool and Git/network dependency
  • Template release can drift from crates
Alternative

Install script

Pipe a hosted shell script that downloads project files.

  • Fast initial implementation
  • Harder to trust and support cross-platform
  • Always network-coupled
Generated shape

A real application, not a fragile snippet

my-app/ ├── Cargo.toml ├── Makefile ├── .env.example ├── .gitignore ├── migrations/ │ └── 00000000000000_arc_base/ │ ├── up.sql │ └── down.sql ├── src/ │ ├── main.rs │ ├── config.rs │ ├── routes.rs │ └── domain/ │ └── mod.rs ├── tests/ │ └── smoke.rs └── resources/ # only with --ui ├── views/ └── assets/

Ownership boundary

Arc crates own framework behavior. The generated project owns deployment choices: migrations, ports, secrets, routes, and domain code.

Why migrations are copied: database migrations are application state. Embedding them implicitly inside arc-web caused the published 0.2.2 build failure; the scaffold makes their location explicit and testable.

Plain arc new my-app stays deliberately small. arc new my-app --ui adds the full Tera/frontend application without burdening API-only apps.

Implementation slices

Small, releaseable steps

1

Scaffolder crate

Add publishable arc-web-cli with the arc binary, argument parsing, project-name validation, embedded templates, and safe refusal to overwrite.

2

Minimal template + UI overlay

Generate the lean server contract by default. When --ui is present, overlay Tera views, frontend assets, and UI routes from the same embedded release.

3

Setup contract

make setup idempotently creates local config/secrets, installs required frontend tools only when selected, and migrates SQLite.

4

External proof

Package crates, install CLI from the package, generate outside the workspace, build, start on a free port, probe health, and clean up.

5

Publish and replace the tutorial

Publish arc-web-cli, then make the five-command path the README’s primary quick start. Keep repository cloning only for Arc contributors.

Guardrails

Definition of done

Acceptance checks

  • A user can start from an unrelated empty directory; no Arc repository files are assumed.
  • Generated dependency versions match the CLI/template release.
  • Plain generation has no frontend toolchain; --ui produces a buildable Tera/assets starter.
  • make setup is safe to run twice and never replaces an existing secret.
  • A busy port produces a visible error naming the port and the override variable.
  • A missing/unwritable database produces a visible error before exit.
  • Clean-room smoke tests prove both profiles through generate → setup → build → serve → health.

Not in v1

  • Interactive TUI wizard
  • Postgres/NATS provisioning
  • Automatic project upgrades
  • Plugin marketplace
  • Production deployment
